# 小原 AI 查询能力矩阵与输入输出示例

本文档描述当前代码已经实现的能力，不把规划中的字段、交互或模型理想行为写成现有能力。
可用它做产品评审、Prompt 验收和回归测试。

状态说明：

- **支持**：Tool、Skill 和确定性代码已经覆盖。
- **部分支持**：主流程可完成，但数据字段、候选控制或 UI 仍有限制。
- **不支持**：当前接口、Tool Schema 或界面没有这项能力。

## 1. 总体处理边界

```text
用户自然语言
  → Agent 判断意图、提取条件、识别歧义
  → Skill 决定是否查询、追问或创建预约草稿
  → Tool 校验结构化参数
  → 外部接口返回宽结果
  → Tool 执行精确过滤、条件求交和零结果诊断
  → Agent 只围绕用户原问题组织回答
```

通用规则：

1. 未提供的可选条件不参与过滤；显式空值和非法格式不会被静默当成“未提供”。
2. 多个查询条件都是 AND 关系，系统不会偷偷删除错误条件扩大查询。
3. “正常但没找到”与“外部服务异常”严格区分。
4. Tool 返回事实和诊断码，Agent 负责用自然语言解释，不编造候选或查询结果。
5. 回答只展示当前问题需要的字段，避免无关人员信息或会议室信息进入上下文。

## 2. 找人能力

### 2.1 当前支持的查询条件

| 条件 | Tool 参数 | 匹配方式 | 示例 | 状态 |
|---|---|---|---|---|
| 完整工号 | `employee_id` | 规范化后精确相等 | `工号001849是谁` | 支持 |
| 省略前导零的工号 | `employee_id` | 1至5位纯数字左补零到6位 | `工号1849是谁` → `001849` | 支持 |
| 完整手机号 | `phone` | 去除常见分隔符后精确相等 | `18612345678是谁的手机号` | 支持 |
| 手机号尾号 | `phone_suffix` | 手机号以指定数字结尾 | `手机尾号3987是谁` | 支持 |
| 完整姓名 | `name` | 姓名精确相等 | `帮我找张鹏飞` | 支持 |
| 姓名片段 | `name_fragment` | 姓名包含指定文字 | `找名字里有“鹏”的同事` | 支持 |
| 多条件组合 | 上述参数组合 | 各条件结果按工号取交集 | `工号1849、尾号3987的人` | 支持 |
| 部门单独查询 | 无 | 当前没有 `department` 查询参数 | `找数字化部所有人` | 不支持 |
| 岗位、机构、办公地点查询 | 无 | 当前接口映射和 Tool Schema 均未提供 | `找上海办公室的产品经理` | 不支持 |
| 拼音、同音字、错别字模糊匹配 | 无 | `name_fragment` 只做文字包含，不做语义纠错 | `朋飞`自动纠正成`鹏飞` | 不支持 |

当前 `PersonInfo` 能返回：

| 字段 | 含义 | 当前可用性 |
|---|---|---|
| `employee_id` | 工号 | 支持 |
| `name` | 姓名 | 支持 |
| `phone` | 手机号 | 支持，取外部接口可用电话字段 |
| `email` | 邮箱 | 支持，外部接口未提供时为空字符串 |
| `department` | 部门 | 支持，外部接口未提供时为空字符串 |
| 机构 | 所属机构 | 不支持独立字段 |
| position | 岗位 | 不支持 |
| officeLocation | 办公地点 | 不支持 |

### 2.2 输入与预期行为

| 分类 | 用户输入示例 | 系统处理 | 预期用户侧输出 | 状态 |
|---|---|---|---|---|
| 完整姓名 | `帮我找一下张鹏飞` | 调用 `find_person(name="张鹏飞")` | 唯一命中时说明姓名和完成问题所需字段；重名时展示必要候选 | 支持 |
| 查询联系方式 | `王鹏的手机号是多少` | 按完整姓名查询；不自动改成姓名片段 | 唯一命中时只回答手机号及必要身份信息 | 支持 |
| 标准工号 | `查一下工号001849` | 按工号精确查询 | 返回匹配员工的必要信息 | 支持 |
| 短工号 | `工号1849是谁` | 自动规范化为`001849` | 不追问工号还是手机号 | 支持 |
| 完整手机号 | `18612345678是谁的手机号` | 按完整手机号精确查询 | 返回号码所属员工；多人异常命中时展示候选 | 支持 |
| 带分隔符手机号 | `186-1234-5678是谁` | Schema 接受常见分隔符，Tool 提取数字后精确匹配 | 按规范化号码返回结果 | 支持 |
| 手机尾号 | `手机尾号3987是谁的` | 调用 `phone_suffix="3987"` | 唯一命中时直接回答；多人时展示必要候选 | 支持 |
| 明确尾号语义 | `3987是谁的手机号` | “手机号”已消除歧义，按尾号查询 | 不再追问是工号还是手机号 | 支持 |
| 纯数字歧义 | `3987是谁`、`帮我查一下1849` | 不调用Tool，先询问按工号还是手机号尾号 | 文本询问用户选择查询含义 | 支持 |
| 纯数字可点击选项 | `3987是谁` | 当前前端没有此处专用快捷选项 | 只能文本追问，不能保证出现可点击按钮 | 不支持 |
| 姓名片段 | `找一个名字里有鹏的同事` | 调用 `name_fragment="鹏"` | 候选较少时展示必要候选；候选多时请求进一步缩小 | 部分支持 |
| 不完整姓名 | `帮我找一下朋飞` | 只有模型明确判断这是姓名片段时才按字面`朋飞`查询 | 只匹配真实姓名中包含“朋飞”的人，不会自动匹配“鹏飞” | 部分支持 |
| 重名 | `帮我找张伟` | 完整姓名查询可能返回多人 | 展示工号、部门等已有字段供确认，不泄露无关联系方式 | 支持 |
| 候选过多 | `找名字里有王的同事` | Tool 最多请求外部接口前100条；当前没有固定候选阈值或分页协议 | Agent 应展示少量必要候选并请求更多线索 | 部分支持 |
| 核对说法 | `工号001849、尾号3987的人是不是张鹏飞` | 只用工号和尾号查询，再比较返回姓名；`张鹏飞`不是过滤条件 | 命中后回答姓名是否一致 | 支持 |
| 单条件不存在 | `工号999999是谁` | 返回 `condition_not_found`，条件为`employee_id` | 明确该工号没有匹配，不编造人员 | 支持 |
| 某个组合条件错误 | `工号001849、尾号9999的人` | 若工号有结果而尾号无人命中，返回尾号条件无匹配 | 指出尾号线索没有匹配，请用户核对 | 支持 |
| 条件指向不同人员 | `工号001849、尾号3987的人` | 若两个条件分别匹配不同员工，返回 `conditions_conflict` | 说明线索不属于同一员工，请用户确认哪个条件正确 | 支持 |
| 显式空值 | 模型传`employee_id=" "`或`name_fragment=""` | Schema 在请求外部接口前拒绝 | Agent 根据原话重新提取；无法唯一修正时追问 | 支持 |
| 非法手机号文本 | 模型传`phone_suffix="尾号3987"` | Schema 拒绝，Tool 参数只能是数字及常见分隔符 | Agent 应提取为`3987`后再调用；无法提取时追问 | 支持 |
| 掩码手机号 | `186XXXXXXXX是谁` | 不是完整可查询号码，也不是纯数字尾号 | 请求用户提供可查询的完整号码或明确尾号 | 不支持直接查询 |
| 外部服务异常 | 人员接口超时或报错 | 返回 `error.code=service_error`，不暴露内部错误详情 | 说明当前查询服务异常，不能回答“查无此人” | 支持 |

### 2.3 找人 Tool 输出语义

唯一或多个共同匹配：

```json
{
  "people": [
    {
      "employee_id": "001849",
      "name": "张鹏飞",
      "phone": "18612343987",
      "email": "zhangpengfei@example.com",
      "department": "数字化部"
    }
  ],
  "error": null
}
```

某个条件自身没有匹配：

```json
{
  "people": [],
  "error": null,
  "noMatch": {
    "reason": "condition_not_found",
    "conditions": ["phone_suffix"]
  }
}
```

各条件分别有人命中，但没有共同员工：

```json
{
  "people": [],
  "error": null,
  "noMatch": {
    "reason": "conditions_conflict",
    "conditions": ["employee_id", "phone_suffix"]
  }
}
```

### 2.4 用户侧回答示例

以下是回答语义示例，不要求模型逐字复述：

| 输入 | 假设查询事实 | 合格回答示例 |
|---|---|---|
| `工号1849是谁` | `001849`唯一命中张鹏飞 | `工号001849是张鹏飞，所属部门为数字化部。` |
| `张鹏飞的手机号是多少` | 唯一命中，电话为18612343987 | `张鹏飞的手机号是18612343987。` |
| `3987是谁` | 数字含义不明确 | `你想按工号查询，还是按手机号尾号查询？` |
| `手机尾号3987是谁` | 两名员工尾号相同 | `尾号3987匹配到两位员工：张鹏飞（数字化部，工号001849）和王鹏（财务部，工号001730）。请确认你要找哪一位。` |
| `工号001849、尾号9999的人` | 尾号9999自身无匹配 | `没有查询到手机尾号9999对应的员工，请核对尾号。` |
| `工号001849、尾号3987的人` | 两个条件分别指向不同员工 | `工号001849和手机尾号3987没有指向同一位员工，请确认哪条信息需要更正。` |
| `工号999999是谁` | 查询正常但无匹配 | `没有查询到工号999999对应的员工。` |
| 相同问题但人员服务报错 | `service_error` | `当前人员查询服务异常，暂时无法确认；这不代表该员工不存在。` |

## 3. 会议室能力

### 3.1 当前支持的查询条件

| 条件 | Tool 参数 | 匹配方式 | 状态 |
|---|---|---|---|
| 单楼层 | `floor` | 正整数楼层，外部接口的查询粒度 | 支持，查询必填 |
| 房间名称或房间号 | `roomQuery` | 去空格、去“会议室”后精确匹配 | 支持 |
| 外部会议室ID | `roomQuery`或`roomId` | 查询时精确匹配；创建草稿时使用准确`roomId` | 支持 |
| 日期 | `time.date` | 单次查询一天；省略默认今天 | 支持 |
| 准确时段 | `time.start/end` | 两者必须同时提供，按时间区间判断 | 支持 |
| 全天时间表 | `time={}` | 返回今天当前可预约时间起的时间表 | 支持 |
| 最小容量 | `requirements.minCapacity` | 房间容量大于等于人数 | 支持 |
| 设备 | `requirements.equipment` | 必须同时具备列表内全部设备 | 支持 |
| 只看空闲 | `requirements.availableOnly` | 只保留目标时段完整可用的房间 | 支持，必须有准确时段 |
| 多条件组合 | 上述条件组合 | 固定过滤管道逐层求交 | 支持 |
| 多楼层 | 多次调用`search_meeting_rooms` | Agent 可并行查询，一轮最多5层 | 支持 |
| 多日期/周期日程 | 多次单日查询 | 没有跨日或周期查询参数 | 部分支持 |
| 周期预约 | 无 | 当前只创建单日、单时段草稿 | 不支持 |

会议室查询结果按问题裁剪，但候选始终包含 `roomName` 和 `roomId`。可能返回的字段包括：

- 静态字段：`roomName`、`roomId`、`floor`、`capacity`、`equipment`。
- 时间字段：`timeline`、`availableTimeRanges`、`isAvailable`、`conflicts`。
- 查询诊断：`matchedRoomCount`、`emptyReason`、`observedAt`。

### 3.2 输入与预期行为

| 分类 | 用户输入示例 | 系统处理 | 预期用户侧输出 | 状态 |
|---|---|---|---|---|
| 楼层静态查询 | `7楼有哪些会议室` | `floor=7`，省略`time` | 返回7楼房间名称、roomId及必要静态信息 | 支持 |
| 指定房间静态信息 | `707会议室能坐多少人` | 从707推断7楼，传`roomQuery="707"` | 只回答707的容量，不附加无关日程和其他房间 | 支持 |
| 指定房间设备 | `707有视频会议设备吗` | 推断7楼并精确过滤707 | 只回答该房间设备情况 | 支持 |
| 今天完整日程 | `看看7楼今天的会议室安排` | `floor=7,time={}` | 返回今天当前可预约时间起的时间表 | 支持 |
| 指定日期日程 | `看一下7楼明天的安排` | 把“明天”换算为绝对日期，`time={date}` | 返回指定日期时间表 | 支持 |
| 指定房间可用性 | `707明天14:00到15:00能用吗` | 推断7楼；保留707，不传`availableOnly` | 返回`isAvailable`；占用时同时说明冲突时间和占用方 | 支持 |
| 只给开始时间 | `707明天下午2点能用吗` | 默认持续60分钟，查询14:00-15:00 | 告知这一小时是否可用 | 支持 |
| 找空闲房间 | `找7楼明天14:00到15:00空闲的会议室` | `availableOnly=true`，人数未给时容量默认按5人 | 只返回完整时段可用的候选 | 支持 |
| 容量筛选 | `找7楼能坐20人的会议室` | `minCapacity=20` | 返回容量至少20人的房间 | 支持 |
| 设备筛选 | `找7楼有白板和视频会议的房间` | 两项设备作为AND条件 | 只返回同时具备两项设备的房间 | 支持 |
| 复合筛选 | `7楼明天14点找能坐10人、有视频会议的空闲房间` | 楼层、日期、默认60分钟、容量、设备、空闲一次求交 | 返回全部条件共同命中的房间 | 支持 |
| 多楼层 | `查7、8、9楼明天14点的空闲会议室` | 并行调用3次，每层一次 | 合并说明各楼层候选 | 支持 |
| 超过5个楼层 | `查1到10楼空闲会议室` | 不一次发起10个查询 | 请求用户缩小到最多5个楼层 | 支持边界控制 |
| 只给时间 | `帮我找明天下午2点的会议室` | 楼层无法推断 | 先询问楼层，不调用Tool | 支持 |
| 只给房间号 | `808明天下午2点能用吗` | 编号前缀推断8楼 | 查询8楼808，不额外追问楼层 | 支持 |
| 楼层与编号冲突 | `8楼的606明天下午2点能用吗` | 606按编号规则属于6楼，与8楼冲突 | 不调用Tool，询问是8楼还是606会议室 | 支持 |
| 外部roomId缺少楼层 | `查roomId=165的日程` | roomId不能推断楼层，而查询Tool要求楼层 | 询问楼层；不能把165解释为房间号 | 支持边界控制 |
| 指定房间不存在 | `7楼708会议室怎么样` | 7楼数据内精确匹配708 | 返回该楼层没有此房间，不展示其他房间代替 | 支持 |
| 楼层无数据 | `99楼有哪些会议室` | 上游无该楼层有效房间 | 说明该楼层没有返回会议室数据 | 支持 |
| 容量不满足 | `找7楼能坐100人的会议室` | 前序候选在容量筛选层归零 | 说明没有满足容量要求的房间，不删除人数条件 | 支持 |
| 设备不满足 | `找7楼有录音棚的会议室` | 设备筛选归零 | 说明没有具备该设备的房间 | 支持 |
| 时段无空闲 | `找7楼14:00到15:00空闲的会议室` | `availableOnly`筛选归零 | 说明该时段没有空闲房间 | 支持 |
| 房间被占用 | `707在14:00到15:00能用吗` | 不用`availableOnly`删除707 | 明确不可用，并返回冲突时间及可用的占用方字段 | 支持 |
| 空房间名 | 模型传`roomQuery=" "` | Schema 在外部查询前拒绝 | 重新从原话提取；无法确定时追问 | 支持 |
| 空设备名 | 模型传`equipment=[""]` | Schema 拒绝，不把空列表当成无设备要求 | 重新提取或追问 | 支持 |
| 非正楼层 | `0楼有哪些会议室` | `floor`必须大于0 | 询问正确楼层，不调用外部会议室查询 | 支持 |
| 时段格式错误 | `7楼25点有空房吗` | 无法形成合法`HH:mm` | 请求用户提供有效时间 | 支持 |
| 营业时间外 | `7楼晚上8点有空房吗` | 超出09:00-18:30 | 说明可查询/预约时段并请用户调整 | 支持 |
| 外部服务异常 | 会议室接口超时或报错 | `success=false`，不伪装成零候选 | 说明查询服务异常，不回答“没有会议室” | 支持 |

### 3.3 会议室零结果输出语义

`matchedRoomCount=0`时，`emptyReason`表示过滤管道中第一个令候选归零的阶段：

| `emptyReason` | 用户侧含义 |
|---|---|
| `floor_has_no_rooms` | 该楼层没有返回有效会议室 |
| `room_not_found_on_floor` | 该楼层不存在指定房间名称或roomId |
| `no_room_meets_capacity` | 没有房间满足最小容量 |
| `no_room_has_required_equipment` | 没有房间同时具备要求的设备 |
| `no_room_available_in_time` | 没有房间在指定时段完整可用 |
| `no_matching_rooms` | 兜底诊断；当前固定管道正常情况下很少出现 |

示例：

```json
{
  "success": true,
  "floor": "7F",
  "matchedRoomCount": 0,
  "rooms": [],
  "roomQuery": "708",
  "emptyReason": "room_not_found_on_floor"
}
```

### 3.4 预约草稿与真实写操作

| 分类 | 用户输入示例 | 系统处理 | 预期结果 | 状态 |
|---|---|---|---|---|
| 创建预约草稿 | `帮我订707明天14:00到15:00` | 先取得准确`roomId`，再重查最新状态 | 空闲时生成`meetingRoomBookingDraft`卡片 | 支持 |
| 未给人数 | `帮我订707明天14点` | 时长默认60分钟，人数默认5人 | 生成14:00-15:00、5人的草稿 | 支持 |
| 未给主题 | 同上 | 使用当前鉴权用户名生成默认主题 | 草稿中展示默认主题，可在卡片流程中处理 | 支持 |
| 预约前冲突 | 目标时间已被占用 | `book_meeting_room`再次读取最新状态 | 不创建草稿，返回占用方和占用时间 | 支持 |
| roomId不存在 | 模型传错误roomId | 重查未找到房间 | 不创建草稿，说明房间不存在 | 支持 |
| 过去时间 | 预约今天已经过去的时间 | 服务端事务校验拒绝 | 不创建草稿 | 支持 |
| 非半小时边界 | `14:10到15:10`并要求预约 | 预约只接受整点或半点边界 | 请用户调整时间，不创建草稿 | 支持 |
| 真实预约 | 用户只在聊天里说“确认” | 模型没有真实预约Tool | 不执行真实预约 | 支持安全边界 |
| 卡片确认 | 用户在预约卡片界面确认 | 服务端确认前再次校验并调用真实预约接口 | 成功后产生真实预约记录 | 支持 |
| 草稿取消 | 用户点击卡片取消 | 本地草稿变为cancelled | 不调用真实预约接口 | 支持 |
| 模型直接取消草稿 | 用户要求助手取消旧卡片 | 模型没有确认/取消卡片Tool | 引导用户操作卡片 | 不支持模型操作 |
| 周期预约或批量预约 | `每周一订707` | 当前无周期草稿和批量确认状态机 | 说明当前限制 | 不支持 |

### 3.5 用户侧回答示例

以下示例中的房间和时间结果是假设事实，用于约束回答方式：

## 4. 建议人工验收用例

### 4.1 找人

1. `帮我找一下张鹏飞`
2. `查一下工号1849`
3. `18612345678是谁的手机号`
4. `手机尾号3987是谁的`
5. `3987是谁`
6. `找名字里有鹏的同事`
7. `工号001849、尾号3987的人是不是张鹏飞`
8. 故意把存在的工号与错误尾号组合。
9. 故意把两个分别属于不同员工的条件组合。
10. 输入不存在的工号、空姓名、非法手机号和掩码手机号。

### 4.2 会议室

1. `7楼有哪些会议室`
2. `707能坐多少人`
3. `看看7楼明天的安排`
4. `707明天下午2点能用吗`
5. `找7楼明天下午2点空闲的会议室`
6. `找7楼能坐10人、有视频会议的空闲会议室`
7. `查7、8、9楼明天下午2点的空闲会议室`
8. `帮我找明天下午2点的会议室`
9. `8楼的606明天下午2点能用吗`
10. 查询不存在的房间、没有数据的楼层、过大容量和不存在设备。
11. 查询已占用房间，确认系统保留该房间并说明冲突。
12. 创建预约草稿后，不点击卡片，只在聊天中说“确认”，确认不会真实预约。

## 5. 当前最值得补充的能力

以下是文档与当前能力对照后比较明确的后续项：

1. 人员接口补充机构、岗位和办公地点字段，才能按这些维度展示或筛选候选。
2. 为姓名片段查询增加明确的候选上限、分页或二次筛选协议。
3. 如需纯数字歧义的可点击选项，需要恢复或重新设计当前轮快捷选项 UI。
4. 如需拼音、同音字和错别字查人，需要新增独立检索策略，不能冒充现有`name_fragment`。
5. 如需多日期、周期或批量会议室预约，需要新的批量草稿状态机和逐项人工确认策略。
